## Executive summary

The phase was effective in the narrow sense that it shipped what it specified.
Six PRs (#540–#546) landed S0 through S5 in a single day, each with a spec
committed, each with Layer-0 tests, each with docs, and the one slice whose
output is a judgement rather than a diff — the Assayer — was forward-tested in
two fresh contexts against positive and negative fixtures, with the result
written down including what it does not establish
(`tdad_tests/layer0_deterministic/fixtures/assay_seed/RESULTS-2026-08-23.md`,
`observed`).

The single most important opportunity is not in the mechanism. It is that
**the epic cited its own authority to a document that is not in the
repository, ten days after the previous epic was fixed for exactly that**
(`1133b9c`, 2026-08-13, "Point the epic's provenance at something retrievable,
and transcribe the charter"). Six specs say `**Provenance:** the Harness
Assayer / Harness Registrar build spec, supplied in conversation 2026-08-23`,
then make thirteen claims about what that spec says — including four
deliberate deviations from it. A reader cannot check any of them. The earlier
fix produced a charter file and no rule, so nothing carried forward.

That is the shape the assay exists to catch: a defect fixed once, as an
incident, recurring in the next epic because the fix had no owner.

## Findings

### finding-1 — An epic's authority cited to a document nobody else can open

Six specs — `2026-08-23-harness-evolution-s0` through `-s5` — carry the line
`**Provenance:** the Harness Assayer / Harness Registrar build spec, supplied
in conversation 2026-08-23`. No such document exists in the repository. The six
specs then make thirteen separate claims about what that spec says, and four of
them are recorded deviations from it: S0 §7 "This is the fix for an
unimplementable clause in the build spec", S2 §2 "The build spec's compilation
model does not survive contact with this repo", S4 §132 "The build spec
requires `provisional: true` with a mandatory `expires` date", S5 §35 "The
build spec's example line does not say whether 'expired' appears in the feed".
Each deviation is argued, and none can be checked, because the thing deviated
from is not retrievable.

This is a recurrence, not a first occurrence. Commit `1133b9c` (2026-08-13,
#518) is titled "Point the epic's provenance at something retrievable, and
transcribe the charter" and its message reads: "Seven specs cited a deck that
never existed — it was a label for a build spec supplied in conversation…
those specs cite constitutional constraints BY NUMBER, fifteen times across
seven distinct constraints, against a list that was nowhere in the repository."
The fix produced `docs/superpowers/cadence-sentinels-charter.md`, transcribing
all nine constraints verbatim. It produced no rule. Ten days later the next
epic reproduced the defect at the same scale.

The 2026-08-13 reflection entry did promote a sibling constraint — *Specs cite
the source of a claimed convention* — but scoped it to claims about existing
repository conventions, not to the source document a spec names as its
authority. The narrower half was generalised; the wider half was not.

```yaml
classification: harness-loop
enforcement: advisory
surfaces: [claude-code, codex, cursor, copilot, windsurf]
priority: P2
evidence:
  - docs/superpowers/specs/2026-08-23-harness-evolution-s0-schema-validator-design.md
  - docs/superpowers/specs/2026-08-23-harness-evolution-s2-compile-check-design.md
  - docs/superpowers/cadence-sentinels-charter.md
  - HARNESS.md
overfitting_risk: low
```

**Why this is a tightening, not a new rule.** `HARNESS.md` already carries
*Specs cite the source of a claimed convention*, agent-enforced by the
advocatus-diaboli spec gate, driven by the same class of failure. It cannot
absorb this behaviour as written because its subject is a **claim about the
repository** ("the pattern here is X"), verifiable by opening a file that
exists; this finding's subject is a **source outside the repository**, where
there is no file to open. The rule below extends that constraint's scope rather
than adding a second heading, and the proposed text is written to sit inside
it.

**Overfitting risk: low.** Two independent occurrences, two different epics,
two different authors' sessions, thirteen and fifteen citation instances
respectively. The rule does not encode either epic's specifics.

**Validation plan.** Take the six harness-evolution specs as the negative
fixture: under the rule they must fail the spec gate. Take
`cadence-sentinels-s1` post-`1133b9c` as the positive fixture: it cites
`cadence-sentinels-charter.md` by path and must pass. If the gate cannot
separate those two without reading either spec's content, the rule is not
falsifiable and should be refused.

#### Proposed rule

````markdown
- **Rule**: A spec that names a source document as its authority — a
  provenance line, a "build spec", a charter, a deck, a briefing, a
  conversation — must cite something a second reader can open: a path
  inside this repository, or a URL. Where the source was supplied in
  conversation, transcribe it into `docs/superpowers/` as the first commit
  of the epic and cite that file by path. A spec that departs from its
  cited authority must name the clause it departs from. This extends
  *Specs cite the source of a claimed convention* from claims about
  repository conventions to the sources a spec treats as authoritative:
  the same failure one level up, where there is no file to open at all.
  Specs with filename date before 2026-08-25 are exempt.
- **Enforcement**: agent
- **Tool**: advocatus-diaboli (spec-mode gate)
- **Scope**: pr
````

#### Cost estimate

Roughly fifteen to forty minutes once per epic, paid by whoever writes the
first spec: transcribing a conversation-supplied brief into
`docs/superpowers/` and committing it before the spec that cites it. Zero for
every later spec in the epic and zero for specs with no external authority,
which is most of them. Per-spec it adds one line the diaboli must resolve, and
a spec that cites nothing external passes untouched.

Three ways it can be gamed, in descending order of likelihood. **A transcript
that is not the source** — committing a paraphrase, or the parts that support
the design, and citing that; the path resolves and the check is satisfied while
the deviations remain uncheckable, which is the failure this rule is aimed at,
surviving intact. **Citing a URL that requires credentials, or one that will
rot** — the rule as written accepts any URL and cannot tell an open link from a
private workspace. **Dropping the provenance line entirely** — a spec that
names no authority is not covered, so the cheapest evasion is to stop
attributing, which would cost more than the rule saves. The first is the one to
watch, and it is why the "name the clause you depart from" half is load-bearing
rather than decorative: a paraphrase transcript makes that half impossible to
write honestly.

### finding-2 — The periodic check suite stops at its first failure, and reports the rest as nothing

`.github/workflows/gc.yml` runs nineteen declared GC rules as sequential steps.
Only the final `Summary` step carries `if: always()`. Every rule step therefore
depends on its predecessor succeeding.

On the 2026-08-24 run, step 5 (*GC: Snapshot staleness*) failed and steps 6
through 14 are recorded `skipped` — *Sentinel integrity*, both shell-script
checks, all three plugins' *Release tag completeness*, *Observability archive*,
*Reflection log archival of promoted entries*, and *Affordance review
staleness* (`observed`, run 32712709028, per-step conclusions). On the five
runs before it — 2026-07-20 through 2026-08-17 — *Release tag completeness*
failed at step 9 and steps 10 through 14 did not run (`observed`, run history
and step conclusions).

So for six consecutive weeks the repository received a single red signal that
named one rule, while between five and nine other rules produced no result at
all. Two of the silenced rules are the ones that watch the learning loop
(*Reflection log archival*) and the observability corpus (*Observability
archive*). Nothing in the run summary distinguishes a rule that passed from a
rule that never ran, and a reader checking "did GC pass?" sees one failure
rather than one failure and nine unknowns.

The masking is bidirectional and this window shows both directions. Before
2026-08-24, an unsatisfiable release-tag check hid everything after it. On
2026-08-24 a newly-actionable signal — the snapshot at
`observability/snapshots/2026-07-21-snapshot.md` crossing the 30-day threshold
declared in HARNESS.md — moved to the front and hid the release-tag failure
that is still there.

```yaml
classification: script-validator
enforcement: validated
surfaces: [ci]
target: .github/workflows/gc.yml
priority: P1
evidence:
  - .github/workflows/gc.yml
  - HARNESS.md
  - observability/snapshots/2026-07-21-snapshot.md
overfitting_risk: low
```

**Why this layer, and why no existing owner absorbs it.** `/harness-gc` owns
running the rules and reporting their individual results, and it would have
found both failures on demand — which is why "the release tags are missing" and
"the snapshot is stale" are rejected candidates below, not findings. What
`/harness-gc` cannot own is the behaviour of the scheduled runner when nobody
invokes it: the whole value of a weekly job is the weeks nobody looks. This is
a defect in a validator, and the remedy is a change to that validator, so
`script-validator` is where it sits. It is deliberately not `harness-loop`: the
nineteen rules are correct as declared, and routing this to `HARNESS.md` would
be classifying at the layer that feels most decisive rather than the one that
owns the behaviour.

**Overfitting risk: low.** The rule states a property of any periodic check
suite and encodes neither of the two rules that happened to fail. It would have
applied identically on any of the six runs.

**Validation plan.** Re-run the workflow with a deliberately failing early step
and assert that (a) every later step still produces a conclusion, (b) the job
still concludes `failure`, and (c) no step reports `skipped` for a reason other
than an explicit condition. The third assertion is the one that matters: a fix
that makes the job green by tolerating failures is worse than the defect.

#### Proposed rule

````markdown
- **Rule**: A periodic check suite must produce a result for every rule it
  declares, in every run. A failing rule may not prevent a later rule from
  running: each rule step in `.github/workflows/gc.yml` carries
  `if: always()`, and the job's conclusion is derived from the collected
  results rather than from the first failure. A rule that did not run is
  reported as not run — never omitted, and never counted as passing. The
  point of a weekly job is the weeks nobody reads it, so a run that
  silently stops partway is a run that reports a smaller world than it
  checked.
- **Enforcement**: deterministic
- **Tool**: `.github/workflows/gc.yml` (weekly schedule)
- **Scope**: pr
````

#### Cost estimate

One-off: adding `if: always()` to fourteen steps and a final aggregation step
that fails the job when any collected result failed — perhaps thirty minutes,
once. Recurring cost is the honest one and it is not zero: the weekly run stops
reporting one failure and starts reporting between one and ten, so the first
few weeks after the fix will look worse than the six weeks before it. Whoever
holds the cadence inherits a backlog that was already there and was being
hidden, and the temptation at that moment is to demote whichever rule is
noisiest rather than fix it.

Two ways it can be gamed. **Making the job green rather than complete** —
collecting results and then not failing on them, which satisfies the letter
("a result for every rule") while removing the signal entirely; this is the
likely failure and it is why the rule names the job conclusion explicitly.
**Deleting a chronically-failing rule from the workflow instead of from
`HARNESS.md`** — the rule stays declared, nothing runs it, and the run reports
a complete pass over a smaller set. The second is caught by *Convention parity*
only if someone thinks to check the workflow against the GC section, which
nothing currently does.

### finding-3 — The governance loop shipped complete and governs nothing yet, and that is the correct state

`harness/decisions/` contains `README.md` and `index.md` and no decision
records. `harness/decisions/index.md` reads "No decisions recorded yet" and
`harness/enforcement-report.md` reads "No accepted decisions" (`observed`).
Both CI steps that enforce the mechanism — *Harness decision records are
well-formed* and *Harness governance is applied and undrifted* — are recorded
`success` on PR #546's run, against that empty corpus (`observed`, run
32670266480 per-step conclusions).

Meanwhile `HARNESS.md` carries 36 active constraints, all of which arrived by
hand edit, including two added by the epic itself — *Harness decision records
are well-formed* in S0 and *Harness governance is applied and undrifted* in S2
— and one whose text was hand-reworded in S4 (`observed`, `git show 8a9e02e --
HARNESS.md`). S0 §5.5 designed the migration path for exactly this
(`imported: true`, exempt from the two-assay threshold, `provisional: false`),
and it has not been used.

The tempting finding here is "the mechanism does not govern the document it was
built for". I am not proposing it, for a reason the evidence supports rather
than a charitable one. The three hand edits above all landed *while the
mechanism was being built* — S0 and S2 added the constraints that make the
mechanism enforceable, and S4 reworded one of them as it was still being
specified. There is no observed instance of a constraint being hand-edited
after S5 landed. The only post-epic change to `HARNESS.md` is `1feeaa2` on
`chore/harness-upgrade-0-79-0`, which moved the template marker from 0.73.2 to
0.79.0 and added a commented-out optional `## Stakeholders` block — structural,
not constraint text (`observed`).

So the honest reading is that the corpus is empty because nothing has been
proposed yet, and this assay is the first thing capable of proposing anything.
Recording that is the point. If a second assay observes a constraint hand-added
to `HARNESS.md` after 2026-08-23 without a decision record, this finding
becomes its corroborating observation and the two-assay threshold is met
legitimately. If it does not, this record is the evidence that nothing needed
to change.

```yaml
classification: no-change
enforcement: advisory
surfaces: []
priority: P3
evidence:
  - harness/enforcement-report.md
  - harness/decisions/index.md
  - docs/superpowers/specs/2026-08-23-harness-evolution-s0-schema-validator-design.md
overfitting_risk: low
```

#### Proposed rule

No change.

#### Cost estimate

None. The cost of the alternative — importing 36 legacy constraints as
`imported: true` records to make the corpus non-empty — would be 36 records
whose evidence field cites nothing anyone observed, which is the ceremony this
mechanism exists to replace rather than reproduce.
