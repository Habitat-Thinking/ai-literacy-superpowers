## 1. Purpose

The plugin governs the loop (`HARNESS.md`) and the turn (`AGENTS.md`), but nothing governs how those two documents themselves change. Harness rules currently accrete by hand, without recorded evidence, without a declared enforcement level, without an owner, and without any way to retire them.

This spec introduces two roles that together close the harness evolution loop:

- **The Harness Assayer** — a sentinel. Reads evidence from completed work, classifies what it finds by ownership, proposes a bounded change set, and stops. Read-only with respect to all governance artifacts.
- **The Harness Registrar** — an ordinary agent. Applies human-approved changes, maintains the decision record, compiles governance to each control surface, and reports enforcement gaps. Writes governance, but never authors it.

The separation is the point. An agent that both diagnoses failures and writes the rules can rationalise its own findings into rules that make its next diagnosis easier. Diagnosis and legislation stay in different hands, with a human approval gate between them.

## 2. Non-goals

1. The Harness Assayer does not decide what changes. It proposes; a human accepts.
2. The Harness Registrar does not interpret. If an approved decision record is ambiguous, it stops and asks rather than filling the gap.
3. Neither role commits, pushes, or opens pull requests without separate explicit approval.
4. This is not a general retrospective facilitator for teams. It is scoped to governance artifacts in a repository.
5. No new telemetry collection. The Harness Assayer reads evidence that already exists.

## 3. Vocabulary

| Term | Meaning |
| --- | --- |
| **Governance artifacts** | `HARNESS.md`, `AGENTS.md`, agent instruction files, agent reference files, validator scripts, and the generated regions of each control surface. |
| **Control surface** | A file or mechanism through which governance reaches a tool: `CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md`, `.codex/skills/`, hooks, CI validators. |
| **HDR** | Harness Decision Record. One file per governance change. |
| **Assay** | A read-only postmortem produced by the Harness Assayer. |
| **Enforcement level** | How strongly a rule binds on a given surface: `advisory`, `validated`, or `blocked`. |
| **Promotion** | Moving a finding up to a more durable governance layer. |
| **Demotion** | Retiring or weakening a rule that has expired or lost its evidence. |

## 4. Artifacts and layout

```text
HARNESS.md                          # governs the loop (existing, source of truth)
AGENTS.md                           # governs the turn (existing)
harness/
  surfaces.yaml                     # capability matrix per control surface
  assay/
    <ISO8601>-assay.md              # Harness Assayer output, append-only, never edited
  decisions/
    HDR-<YYYY-MM-DD>-<slug>.md      # one per governance change
    index.md                        # GENERATED by the Harness Registrar
  enforcement-report.md             # GENERATED — per-surface gap report
```

Write permissions, to be enforced by the agents' own instructions and by a validator:

| Path | Harness Assayer | Harness Registrar |
| --- | --- | --- |
| `harness/assay/` | append new files only | read |
| `harness/decisions/HDR-*.md` | read | create and update |
| `harness/decisions/index.md` | read | generate |
| `HARNESS.md`, `AGENTS.md`, agent files, validators | **read only** | update from accepted HDRs only |
| generated regions of control surfaces | **read only** | generate |
| application code, tests, config | **read only** | **read only** |

## 5. The Harness Decision Record

One HDR per governance change. YAML frontmatter plus prose.

```yaml
---
id: HDR-2026-08-19-observed-evidence
title: Require observed evidence for phase completion claims
status: accepted           # proposed | accepted | rejected | superseded | expired
classification: harness-loop
enforcement: validated
surfaces: [claude-code, copilot-cli, codex]
provisional: true
expires: 2026-11-19        # required when provisional
review_trigger: "Two consecutive assays with zero findings in this class"
evidence:
  - harness/build-log.md#2026-08-04T09:12Z
  - harness/assay/2026-08-12T14-03Z-assay.md#finding-3
  - trace://run/8821
proposer:
  agent: harness-assayer
  model: <model-id>
  assay: harness/assay/2026-08-12T14-03Z-assay.md
approver: <human identity>
approved_at: 2026-08-19T10:41Z
cost: |
  Human-authored. One extra check per phase boundary; roughly two minutes.
  Risk: reviewers may start pasting command output to satisfy the rule.
supersedes: null
superseded_by: null
cohort: b                  # optional, for Harness Observatory
---
```

### Identifiers

`HDR-<date>-<slug>`, matching the filename. Sequential numbering collides as soon as two people propose on parallel branches; date-plus-slug is merge-safe and readable in a file listing.

### Body sections, scaled to blast radius

Process burden should be proportional to reach. Two tiers:

**Every HDR:**

1. **Finding** — what was observed, with evidence references. Observed evidence only; reported or inferred evidence must be labelled as such.
2. **Rule** — the exact text to be added, changed, or removed, quoted verbatim as it will appear in the target artifact.
3. **Cost** — human-authored, mirroring the frontmatter field.

**Additionally, for `harness-loop`, `script-validator` and `new-agent`** — the classifications whose reach extends beyond a single agent:

4. **Why this layer** — why the change belongs here and not one layer down.
5. **Enforcement** — how the rule binds on each listed surface, and where it is only advisory.
6. **Validation** — how anyone would know later whether this rule helped.
7. **Rejected alternatives** — including the "no change" option, with the reason it was not taken.

The validator enforces the tier implied by `classification`. Reclassifying upward requires the additional sections before acceptance.

### Classification taxonomy

`harness-loop` · `turn-instructions` · `agent-instruction` · `agent-reference` · `script-validator` · `regression-test` · `new-agent` · `no-change`

`no-change` is a first-class outcome and must be recordable. An assay in which every finding resolves to `no-change` is a successful assay.

## 6. Three loops, three promotion thresholds

Findings enter at the cadence that observed them and must survive the loop above before being promoted.

| Loop | Cadence | Evidence source | May promote to |
| --- | --- | --- | --- |
| **Turn** | Every turn | Turn transcript, AGENTS.md compliance | Phase-level finding only |
| **Phase** | End of a phase or session | Build log, context files, review artifacts, traces | `agent-instruction`, `agent-reference`, `regression-test`, `turn-instructions` |
| **Longitudinal** | Across projects, on Observatory cadence | Multiple assays, cross-cohort signal | `harness-loop`, `script-validator`, `new-agent` |

**Promotion rules the Harness Registrar enforces mechanically:**

- A change to `HARNESS.md` requires evidence from at least two distinct assays in different phases or projects. A single incident cannot reach the loop layer.
- Maximum three accepted HDRs per assay cycle. Excess proposals stay `proposed` and carry forward.
- Every accepted HDR is `provisional: true` on first acceptance, with a mandatory `expires` date (default 90 days) or a `review_trigger`. Permanence is earned at review, not at creation.
- An HDR with an empty `cost` field, or a `cost` field byte-identical to the Harness Assayer's proposal, is refused. The human writes the cost in their own words.

## 7. The Harness Assayer

**Role:** `sentinel`. Read-only trust boundary, advisory output, explicit epistemic honesty.

### Trigger

Invoked explicitly at a phase boundary or on demand (`/harness-assay`). Never self-triggering, never in the middle of implementation work.

### Procedure

1. **Read-only discovery.** Read `HARNESS.md`, `AGENTS.md`, agent files, `harness/build-log.md`, phase context files, review artifacts, prior assays, and the current HDR index. Live repository is the source of truth; do not import assumptions from other projects.
2. **Reconstruct the intended workflow**, then **reconstruct what actually happened**, keeping the two separate.
3. **Apply a materiality test.** A finding is material only if omitting it could change scope, cause repeated discovery, affect an interface or ownership boundary, change acceptance criteria or required verification, affect security, privacy, reliability, observability or recovery, or hide a blocker, assumption or accepted limitation.
4. **Classify each material finding** by ownership using the taxonomy in §5, and state whether the proposed remedy would be advisory or mechanically enforced.
5. **Write the assay report** to `harness/assay/<ISO8601>-assay.md` and stop.

### Assay report structure

- Executive summary — effectiveness and the single most important opportunity
- What worked — evidence-backed practices worth preserving
- What created friction — problem, impact, evidence
- Findings — for each: evidence, classification, proposed rule text, enforcement level, cost estimate, overfitting risk, validation plan, priority `P0`–`P3`
- Rejected candidates — with the existing owner that should absorb the behaviour instead
- Unresolved questions requiring human input

### Hard constraints

- Prefer tightening an existing rule or agent over proposing a new one. State explicitly why the existing owner cannot absorb the behaviour.
- Never propose process solely to make the harness look comprehensive. Every proposal declares its burden.
- Never claim a check, test or integration passed unless the result was observed in evidence. Never convert a planned command from a build file into passing evidence.
- Where evidence conflicts, present both observations and mark the finding unresolved rather than choosing.
- Write nothing outside `harness/assay/`. Propose no commits.
- Stop after the report. Do not draft HDRs, modify governance, or begin forward-testing.

### Optional adversarial pass

Before promotion, an assay may be handed to **Advocatus Diaboli** for adversarial review of the findings themselves — targeting embedded assumptions, evidence strength, and overfitting to this project. Recommended for any finding proposing a `harness-loop` change.

## 8. The Harness Registrar

**Role:** agent, not sentinel. Write authority over governance artifacts, no interpretive authority.

### Commands

| Command | Behaviour |
| --- | --- |
| `/harness-assay` | The Harness Assayer's entry point. See §7. Read-only; writes only its report. |
| `/harness-propose <assay> <finding>` | Draft an HDR at `status: proposed` from an assay finding. Copies evidence references and proposed rule text verbatim; leaves `cost` and `approver` empty. |
| `/harness-accept <HDR>` | The single write transaction. Prompts for `cost` inline, validates the HDR, records approver and timestamp, sets `status: accepted`, applies the rule text verbatim to the target artifact, and recompiles every affected surface. Transactional: if any step fails, nothing is written and the HDR stays `proposed`. |
| `/harness-compile` | Idempotent repair. Regenerates the marked regions of every control surface and `index.md` and `enforcement-report.md` from `HARNESS.md`, `AGENTS.md` and accepted HDRs. Needed only after a hand-edit to a generated region, or after a merge. |
| `/harness-check` | Read-only. Non-zero exit on drift between source and any surface, on an accepted HDR that has not been applied, on an expired HDR still in force, or on an HDR whose evidence references no longer resolve. CI entry point; not something anyone types. |
| `/harness-review` | Run when `/harness-check` reports a lapsed rule. Lists HDRs past `expires` or matching a `review_trigger`; for each, the options are re-evidence, weaken, or demote. Changes still go through `/harness-accept`. |
| `/harness-timeline` | Emits the Observatory intervention feed to stdout. Derived on demand — see §10. |

### Refusals

`/harness-accept` refuses, and writes nothing, on: any missing required field for the HDR's tier; a `cost` left empty or byte-identical to the Harness Assayer's proposal; a missing expiry or review trigger; a promotion-threshold violation; or rule text that does not apply cleanly to the target artifact. It never paraphrases to make text fit.

### Approval gates

Three gates, none implied by another: (1) drafting an HDR, (2) accepting it — which is where the human authors the cost, (3) committing or pushing. Approval for one HDR never generalises to another.

Applying and compiling used to be separate gates. They were removed deliberately: once an HDR is accepted there is no decision left in either step, and a gate with no decision behind it is the exact shape of approval theatre. The two gates that remain are the two where a human is genuinely deciding something — writing the cost, and reviewing the resulting diff.

## 9. Compilation and the enforcement gap

`harness/surfaces.yaml` declares what each surface can actually do:

```yaml
surfaces:
  claude-code:
    targets: [CLAUDE.md, .claude/agents/, .claude/hooks/]
    supports: [advisory, validated, blocked]
  copilot-cli:
    targets: [.github/copilot-instructions.md]
    supports: [advisory]
  codex:
    targets: [AGENTS.md, .codex/skills/]
    supports: [advisory, validated]
  ci:
    targets: [.github/workflows/harness-check.yml]
    supports: [validated, blocked]
```

Compilation writes only inside explicit markers, so hand-written content is never clobbered:

```markdown
<!-- BEGIN GENERATED: harness-registrar — do not edit by hand -->
...
<!-- END GENERATED: harness-registrar -->
```

`harness/enforcement-report.md` states, for every rule on every surface, the intended enforcement level and the achieved one. Where a rule intends `blocked` but the surface supports only `advisory`, that is reported as an enforcement gap, not silently downgraded. **The gap report is a primary output, not a diagnostic.** Knowing which rules are actually enforced and which are merely written down is the point.

## 10. Observatory export

`/harness-timeline` derives the intervention feed from the HDR corpus and writes it to stdout. It is deliberately not a stored artifact: a committed derivative is one more thing that can drift from its source, and `/harness-check` would then have to police it.

One line per accepted, superseded or expired HDR:

```json
{"id":"HDR-2026-08-19-observed-evidence","date":"2026-08-19","classification":"harness-loop","enforcement":"validated","direction":"tighten","surfaces":["claude-code","codex"],"cohort":"b","provisional":true}
```

This is the intervention timeline the difference-in-differences design currently has to infer: when governance changed, in which direction, at what enforcement level, on which cohort.

## 11. Anti-theatre requirements

A well-written postmortem with a prioritised backlog is easy to rubber-stamp; that would be cognitive surrender at the governance layer, which is the worst place for it. The following are requirements, not suggestions:

1. `cost` is human-authored, and the Harness Registrar refuses HDRs where it is not.
2. Three accepted HDRs per cycle, maximum.
3. Rejected candidates are recorded in the assay and surfaced at review time.
4. `no-change` appears as a live option in every assay.
5. Expiry is enforced by CI, not by a calendar. An expired rule still in force fails `/harness-check`, so demotion is never contingent on anyone remembering to reflect.
6. `/harness-check` failing is a build failure, not a warning.

## 12. Operating flow — a worked cycle

The scenario: a three-week slice of work on a client repository. Claude Code has twice reported that the integration suite passed when it had only been planned, and the phase context files have grown to the point where nobody reads them.

### One-time setup

1. Install the plugin. Author `harness/surfaces.yaml` for the tools actually in use on this repository.
2. Run `/harness-compile` once to establish the generated regions in `CLAUDE.md`, `AGENTS.md` and `.github/copilot-instructions.md`. Review the diff; nothing should change except the appearance of the markers.
3. Add `/harness-check` to CI as a required check.

### During the work

Nothing. No harness commands are run mid-phase. The cadence sentinels behave as they always do, the build log accrues, and evidence accumulates as a by-product of working.

### At the phase boundary — roughly twenty minutes

**1. `/harness-assay`**

Reads governance artifacts, build log, context files, review artifacts and prior assays. Writes `harness/assay/2026-08-21T16-02Z-assay.md` and stops. Six findings, two at P1: the unevidenced completion claims, and context files capturing narration that no rule ever asked for.

Read the report. This is the only step that requires real attention.

**2. Adversarial pass (optional, recommended for anything proposing a loop-layer change)**

Hand the assay to Advocatus Diaboli. It kills the context-file finding as overfitted — the bloat came from one unusually exploratory phase, not from a missing rule. That finding stays in the report as a rejected candidate.

**3. `/harness-propose 2026-08-21T16-02Z-assay.md finding-3`**

Drafts `HDR-2026-08-21-unevidenced-completion` at `status: proposed`, copying the evidence references and the proposed rule text verbatim. `cost` and `approver` are left empty.

**4. `/harness-accept HDR-2026-08-21-unevidenced-completion`**

Refused before anything is written: the HDR is classified `harness-loop` but cites evidence from a single assay. Two options — wait for a second assay to corroborate, or reclassify. Here the behaviour belongs to one agent's instructions rather than the loop, so reclassify to `agent-instruction` and re-run.

This time it prompts:

```text
Cost of this rule, in your own words. What will it demand of whoever
works here next, and how might it be gamed?
>
```

Answer in a sentence or two. The command then records you as approver, sets `status: accepted` with `provisional: true` and a 90-day expiry, writes the rule text verbatim into the target agent file, and recompiles every affected surface. `harness/enforcement-report.md` now shows the rule as `validated` on Claude Code and `advisory` on Copilot CLI — an enforcement gap, reported rather than hidden.

**5. Review the diff and commit**

A separate decision. Nothing has been committed on your behalf up to this point.

### The following phase

The rule is in force. The next assay finds the same failure class recurring, but only on Copilot CLI — which is exactly what the enforcement gap predicted. That is now a second, independent piece of evidence, so the finding can be promoted to `harness-loop` and given a validator, making it `blocked` in CI rather than advisory prose.

### When something expires

CI fails: the rule is past its expiry and still in force. Run `/harness-review`. Three options for each lapsed rule — re-evidence it from recent assays, weaken it, or demote it. Demotion produces a superseding HDR, so the record shows the rule existed, what it cost, and why it was retired.

### A quiet cycle

An assay in which every finding resolves to `no-change` is a successful assay and requires no further commands. Recording that nothing needed to change is itself evidence, and the report is the record of it.

## 13. Build phases

Each phase is independently implementable and verifiable, and stops for approval.

- **Phase 0 — Schema and validator.** HDR frontmatter schema including the date-slug identifier and the two body tiers, `surfaces.yaml` schema, and a validator with tests. No agents yet. *Acceptance:* validator rejects each malformed HDR fixture with a specific message; accepts valid ones; enforces the correct body tier for each classification.
- **Phase 1 — Harness Registrar, record-keeping only.** `/harness-propose`, `/harness-accept` in record-only mode, `index.md` generation. *Acceptance:* an HDR can travel proposed → accepted; the inline cost prompt appears and rejects empty or Assayer-identical text; refusals fire for missing expiry and single-evidence loop-layer promotion, leaving the HDR `proposed` and nothing else written.
- **Phase 2 — Apply, compile and check.** Application and recompilation folded into `/harness-accept` as one transaction, plus `/harness-compile` as repair and `/harness-check` in CI, generated markers, enforcement report. *Acceptance:* a rule that does not apply cleanly leaves no partial write and the HDR still `proposed`; hand-editing a generated region fails `/harness-check` and is repaired by `/harness-compile`; hand-written content outside markers survives compilation unchanged.
- **Phase 3 — The Harness Assayer.** Sentinel definition, assay procedure, report template, write-boundary enforcement. *Acceptance:* on a seeded repository with a known workflow failure, the assay identifies it, classifies it correctly, proposes a bounded rule, and writes nothing outside `harness/assay/`.
- **Phase 4 — Review and demotion.** `/harness-review`, expiry detection in `/harness-check`, supersession chains. *Acceptance:* an expired provisional HDR still in force fails `/harness-check`; demotion produces a superseding HDR rather than a silent deletion.
- **Phase 5 — Observatory export.** `/harness-timeline`, cohort tagging. *Acceptance:* the derived feed round-trips against the HDR corpus with no unrecorded interventions, and re-running it produces byte-identical output.

Forward-test Phase 3 in fresh, independent contexts with realistic artifacts, without revealing the seeded defect, and check both positive and negative triggering. Structural validation alone does not constitute evidence that the Harness Assayer works.
