# Enforcement report format

`harness/enforcement-report.md` states, for every accepted rule on every surface
it names, the enforcement level **intended** and the level **achieved**.

> The gap report is a primary output, not a diagnostic. Knowing which rules are
> actually enforced, and which are merely written down, is the point.

It is generated by `/harness-compile` and verified by `/harness-check`. Never
edit it.

## Routing: classification decides where, surfaces decide who is told

Two things that sound alike do different jobs.

- **`classification`** decides which artifact the rule text is written into. One
  accepted record writes to exactly one target.
- **`surfaces`** decides who is told about the rule. The enforcement report is
  what they are told.

`harness/surfaces.yaml` carries both halves:

```yaml
routes:
  harness-loop: HARNESS.md
  turn-instructions: AGENTS.md

surfaces:
  claude-code:
    targets: [CLAUDE.md, .claude/agents/, .claude/hooks/]
    supports: [advisory, validated, blocked]
  copilot:
    targets: [.github/copilot-instructions.md]
    supports: [advisory]
  ci:
    targets: [.github/workflows/]
    supports: [validated, blocked]
```

Classifications with no route — `agent-instruction`, `agent-reference`,
`script-validator`, `regression-test`, `new-agent` — write to the artifact named
by the record's own `target:` field, required at acceptance. Nothing in the
schema can infer it: `agent-instruction` says the behaviour belongs to an agent,
not *which* agent, and that choice is the human's, made at the gate beside the
cost.

### Why compilation does not write into every surface's files

The obvious reading — compile each rule into every surface's instruction file —
puts two generators on one file. In this repository `/convention-sync` already
generates `.github/copilot-instructions.md`, `.cursor/rules/constraints.mdc` and
`.windsurf/rules/constraints.md` from `HARNESS.md`, and a second generator would
emit the same rule twice, in two voices, with each mechanism believing it owned
the outcome.

It is also ambiguous: a surface listing `.claude/agents/` among its targets does
not say which of many files an agent instruction belongs in.

So a rule reaches those surfaces once it is in `HARNESS.md`, and the report says
what actually reaches them rather than claiming a reach the mechanism does not
have.

## Deriving `achieved`

The ladder is `advisory` < `validated` < `blocked`.

1. If `intended` is in the surface's `supports`, the candidate is `intended`.
2. Otherwise the candidate is the highest supported level strictly below
   `intended` — or `none`, when the surface supports nothing lower.
3. **The validator gate.** If the candidate is `validated` or `blocked` and the
   record declares no `validator` resolving to a file that exists, the candidate
   degrades — to `advisory` where the surface supports it, otherwise to `none` —
   and the reason is recorded.

### Step 3 is what earns the report its keep

Without it, a rule declaring `enforcement: blocked` and naming the `ci` surface
reports as blocked while nothing, anywhere, refuses anything.

That is worse than having no report. It is a confident, legible, wrong answer,
produced by the mechanism whose entire purpose is distinguishing *enforced* from
*written down* — and it would be believed, because it is generated.

A **declared but absent** validator is treated exactly like no validator. A path
that does not resolve is the failure this check exists to catch, so believing the
declaration would defeat the mechanism at the one point it bites.

## `validator`

`validator:` on the record — a path, or a list of paths, to the script, workflow,
or hook that actually enforces the rule.

Optional. Its **absence is never an error**: an unenforced rule is not a
malformed one, and refusing it would collapse the distinction the report is built
to preserve.

## Shape

```markdown
# Enforcement report

<!-- BEGIN GENERATED: harness-registrar — do not edit by hand -->

Gaps: 3 of 5 rule-surface pairs.

## HDR-2026-08-19-observed-evidence — Require observed evidence

Target: `HARNESS.md` · classification: `harness-loop`

| Surface | Intended | Achieved | Gap | Why |
| --- | --- | --- | --- | --- |
| claude-code | blocked | blocked | ok | — |
| copilot | blocked | advisory | gap | surface supports at most advisory |
| ci | blocked | advisory | gap | no validator declared or resolvable |

<!-- END GENERATED: harness-registrar -->
```

The same account is also rendered **beside the rule**, in the generated region of
the artifact that owns it:

```markdown
_Intended: blocked · claude-code: blocked · copilot: advisory (gap) ·
provisional until 2026-11-19_
```

A rule that says `blocked` but is merely advisory on the surface someone is
reading should admit that where they are reading it, not only in a report they
may never open.

## A gap is never a failure

`/harness-check` does not fail on an enforcement gap, and neither does the
validator.

Failing would push authors to declare the weakest enforcement any surface
supports, which destroys exactly the information the report exists to carry. A
rule intending more than a surface can deliver is a true and useful fact about
the world.
