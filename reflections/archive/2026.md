- **Surprise**: The PR-time CI suite has no `mkdocs build --strict` step. The strict build is exactly the verification that catches broken-link errors, but it only runs in `pages.yml` on push-to-main as part of the deploy. So the entire shape of "main is broken until we ship a fix" was structurally available: any PR that changes `docs/**` and breaks the build will land on main before anyone notices. Three things are worth recording. **(a) markdownlint is a style linter, not a link validator** — running `npx markdownlint-cli2` locally before pushing felt like docs validation but did nothing for relative-path correctness. The mental model "I lint, therefore I'm covered" was wrong. **(b) MkDocs resolves links from the source file's directory, not from `docs/` root** — obvious in hindsight but invisible without the strict build telling you. The relative-link mental model has to match the build's mental model, and the only way to verify the match is to run the build. **(c) This is the *second* "broken-main + recovery PR" pattern in the same week** — PR #286 → #287 and PR #289 → #290 were the rename+edit gotcha (different mechanism, same shape). Two structurally identical bugs in one week is a signal that the PR-time verification suite has gaps the post-merge environment fills, and the gaps are observable: any time the post-merge environment runs a check the PR doesn't, that gap is at risk of breaking main.
- **Proposal**: Add to AGENTS.md GOTCHAS — "Docs-link relative-path gotcha: when adding a docs page that links to other docs pages, MkDocs resolves links from the source file's directory, not from the docs root.
